# recruiters.rip design system

Required for every product UI change. This document replaces the previous Warm Bone, flat-spectrum, mint/rose status system. It governs the companion and the account/setup website; their source repositories remain independently buildable.

## Source and precedence

- Approved artifact: [recruiters.rip design system](https://claude.ai/artifact/8PZTo24Gv7onffw9MngADm), retrieved 15 October 2026.
- Downloaded source: the current author-written `README.md`, `tokens.json`, component bundle and previews, seven font files and current `assets/Logos` files. The complete download also contains generated component API cards.
- The artifact's generated `tokens.css`, `manifest.json` and some generated API descriptions still contain the previous design. Do not copy those stale values. Current `tokens.json` and the author-written brand rules take precedence. The sample bundle repeats azure at the end of its dispersion declaration; use violet as the fifth stop, as specified by the current palette and brand rules.
- Runtime tokens live in `ui/design-tokens.css` here and `src/app/design-tokens.css` in the website. Their values must agree. Fonts and logos are local assets, not remote dependencies.
- The supplied bundle targets a React global. The website adapts the supplied components to its existing React implementation; the companion uses equivalent semantic HTML. Neither app loads a second framework or imports its sibling at build/runtime.

## Visual principle

**Dark ground, clear surfaces, light at the edge.** Structure comes from fine rules, not rounded tiles, coloured panels or drop shadows. All text ranges left. Colour appears only where a thin edge catches light. This is not frosted-card styling: do not add generic backdrop blur, gradient fields, opaque coloured bands or decorative animation.

Three voices have distinct jobs:

- **Instrument Serif:** upright headlines, section headings and panel titles, never smaller than 28px.
- **Geist Mono:** navigation, buttons, labels, metadata, code and numbers.
- **Geist:** reading copy and field content.

No italics, emoji, decorative serial numbers, centred headlines or chromatic body/link/status text. Keep the brand lowercase: **recruiters.rip**. Product capabilities, privacy claims and status labels must remain true; the artifact's examples are not evidence of features such as an employer posting flow. Warm introductions are real but live only in the connected agent (`career_intro_paths`); the companion has no introductions screen, so never draw one.

### Dispersion

Five stops, in this exact order, blended in OKLab:

| Token | Value |
| --- | --- |
| `color-disperse-red` | `oklch(0.76 0.15 15)` |
| `color-disperse-amber` | `oklch(0.85 0.13 70)` |
| `color-disperse-green` | `oklch(0.86 0.15 150)` |
| `color-disperse-azure` | `oklch(0.80 0.12 250)` |
| `color-disperse-violet` | `oklch(0.78 0.12 295)` |

Use `--rr-dispersion` horizontally and `--rr-dispersion-v` vertically. They are allowed on 1px edges, rules, active-navigation underlines, hover borders and the architectural mark's rim. They are never large-area fills, discrete colour bands, single-hue states or coloured logo fills. A focused input may use a 2px dispersion rule. Azure at 35–45% is allowed for selection and focused-input/lit-edge halos. On a dark ground, a lit rule can emit a static blurred copy of itself; it does not emit on the day theme.

A headline may emphasize at most one word with upright red/azure fringes. The word remains ink, not gradient-filled text. Dispersion is decoration; focus and selection must also have a clear monochrome/text/ARIA signal.

## Layout and shape

- 8px base scale: 8, 16, 24, 32, 40, 64, 80 and 120px.
- Content maximum: 1200px. The content container is centred; text inside it is not.
- Section gap: 80px. Related blocks: 40px. Sibling gap: 16px. Card padding and ordinary grid gutters: 24px.
- Feature entries form a ruled grid without gaps. Do not confuse a CSS page layout with a data grid; actual tabular grids/heatmaps use AG Grid.
- Cards, panels, inputs, dialogs and ledgers: square. Buttons and tags: 2px radius. Circular radii are reserved for genuine status dots.
- Hairlines are 1px. Strong ink rules mark the beginning of a ledger or field. Low-contrast facet rules are structural decoration, not the only boundary identifying an interactive control.
- No lifted-card shadows. The current shadow tokens permit keyboard focus, input halos and dark-only edge glow; `shadow-light-glow` is reserved for a splash and is not a general surface effect.
- Nothing animates. No moving light, hover transforms, pulsing status, shimmer, smooth-scroll animation or layout transitions.

## Shared components and states

### Brand

Use the supplied mirrored Instrument Serif **r** paths. The two feet meet at one point; no extra plinth, slit, line, frame or colour is added. Use current `recruiters-rip-mark.svg`/`-reversed.svg` and lockup assets. Do not redraw the mark using another font. Keep clear space of half the mark's height, minimum mark height 12px; use the supplied favicon cut below 24px. The application icon is the light mark on void. A large architectural mark can have an 8% body and a thin dispersion rim on a dark hero, behind and clear of the content.

### Actions

One primary task per action group: ink fill and canvas text. Secondary buttons are transparent with an ink outline. Low-emphasis actions are text buttons. Mono labels, 44px minimum control height, wrapping rather than clipping at narrow widths. Hover lights the edge, not the whole control. Disabled controls have dust text, no filled background, no hover lighting and `cursor: not-allowed`.

Keyboard focus is a 2px canvas gap followed by a solid 2px ink ring. Never replace it with colour alone. Keep focus visible inside clipped/scrolling containers. Links remain ink; a thin dispersion underline may indicate interaction.

### Fields

A visible label, transparent field and bottom ink rule, not a rounded filled box. Preserve semantic input types, password masking, bounds and validation. Focus uses the two-pixel dispersion rule plus an azure halo and a visible high-contrast keyboard indicator. Native selects keep usable options. Errors have explicit text and `role="alert"`; colour is not an error message.

### Lists, readers and status

Career records are a master/detail list, not a custom table engine. Keep full-result ordering before pagination and readable narrow-screen navigation. Current tabs/records use `aria-current`/`aria-pressed`, text weight and a thin edge or rule, never a mint panel. Do not change data or ranking semantics to match a mockup.

State labels come from actual account, membership, device, lock, request or pre-scan state. Retain loading, empty, error, partial, stale, cancelled and disabled states. Do not infer membership, successful pairing, model completion or permission from the visual design. Notifications remain readable and announced with appropriate status/alert semantics. In the companion the notice (`#notice`) is one top-right toast below the topbar: surface fill, facet rule, one ink left edge, no colour or glow, never a banner that pushes content. Confirmations (copied, saved, allowed) clear themselves after five seconds; errors and in-progress instructions (`Complete sign-in … then return here`) stay until something replaces them.

## Screen designs

### Website

- The website uses dark/void surfaces throughout, the reversed logo and ruled Home / Docs / Downloads / Account navigation. Active routes use one ink-outline frame and semibold text, not stacked underlines. The independently owned frontend records its complete website screen rules in its own `design.md`.
- Public Docs is a task-led reference: install, connect an AI app, import a CV, capture jobs, prepare applications and fill forms. Use readable prose, exact controls, short steps, concrete prompts and an index; avoid marketing panels, repeated disclaimers and setup subtitles. Preserve `#install`, `#connect` and `#extension` deep links.
- Downloads is a compact list of actual distribution files, with short setup steps and collapsed file details. Plugins installed from the companion are not download rows. Published release/availability and permission state must stay truthful.
- Authentication, billing, pairing and signed-device boundaries belong to the website and middleware; loading, pending and error states never imply completion. Career data and provider keys stay off the website. Final reasoning belongs to the user's AI app; optional approved API usage remains separately billed.

### Companion

- Dark/void workspace by default. Compact ruled top navigation with the supplied reversed lockup.
- Navigation is **Me / Jobs / Settings / Help**; Me opens by default. Me is everything about the user: the action row (Import CV, Open exports, Export backup, Connect your agent, and Connect account for job access only while unpaired) above the **CVs / Facts / Preferences / Career** browser. **Preferences** is the visible read-only record of what matching uses: four rows — Direction, Location, Employment, Work. Direction shows target roles, accepted alternatives, avoided roles and the saved direction notes; Location shows places, work modes, relocation, travel and availability; Employment shows types, minimum salary and sponsorship; Work shows responsibility mode, direct reports, review emphasis, technologies, domains and company context. Unknown values say `Not saved`; nothing is inferred from the CV. The connected agent writes these fields through `career_preferences_update`; `acceptedAlternatives` and `excludedRoles` are dedicated fields, not buried in notes. **Career** lists the work history the agent extracted from current CVs and confidently matched to JobStash: one plain row per role (employer as the title; mono summary `Title` then `Mar 2021 – Jan 2024`, `Present` for a current role, `Not stated` for a missing date), newest first, identical roles shown once. Its reader shows Employment (Company, Title, Dates), Inferred from CV (the CV name, plus `CV changed since extraction` when the CV hash moved) and one secondary **Go to {company}’s profile** button; the companion resolves the saved entity ref through the signed relay to the ecosystem.vision page key (`organizations/names/<normalizedName>` or `projects/names/<normalizedName>`) and opens it in the default browser, never a guessed name URL. An employer without an unambiguous page reports `{company} has no public ecosystem.vision page yet.` in the list status. Unmatched employers never appear; the empty state says the agent extracts and links them. Jobs holds ranked jobs, applications and the block list. Settings holds account, chat apps, the optional Decisions API and updates. Help is static and truthful: the exact starting prompt (`Use the recruiters.rip skill to find me a job.`) in a selectable `pre.command`, a four-step how-it-works (connect account → optional pre-filter → agent review → tailor and apply), the docs and downloads URLs as plain `code` text (CSP forbids navigation) and the running package version from state. No marketing copy. Never present a copied prompt as an executing model.
- Jobs is a dedicated full-height tab that conveys one sequence: from a saved CV to a bounded, fresh set of jobs in the user's coding assistant. Above the list sits the **Next agent run** rail (`#run-rail`, mono caption, `ol.run-steps`): normally two recurring ruled columns on wide screens, stacked on narrow ones, each a numbered mono step name, its controls and at most one help line. **Shortlist** is step 1 — the publication slider (`Published in the past 3 days`) above the scope line and Start/Stop, because choosing the window and scoring it are one decision — and **Continue in your AI** step 2. API credentials are setup rather than recurring workflow: prepend **1 · API key** and renumber the recurring steps 2–3 only while no key is saved or a run failed with `PRESCAN_INVALID_KEY`, `PRESCAN_AUTH` or `PRESCAN_KEY_REQUIRED`; it reads `No OpenAI key saved.` with **Add key**, or `Key …ab12 was rejected by OpenAI.` with **Replace key**, and opens Settings → Optional Decisions API. A healthy saved key has no Jobs-rail column; it remains replaceable/removable in Settings. `.run-steps` is two columns, `.has-key-step` three. The current step (`aria-current="step"`) carries the dispersion rule and the single primary button. The slider is five positions — Today, Yesterday, Past 3 days, Past week, Past 2 weeks — labelled `Published in the past 3 days`, with `Today or the past 3 days work best: older listings already have many applicants.`; older saved presets fall back to Past 2 weeks. Shortlist is binary and shows exactly one action: not running shows the scope line (`1,452 jobs in scope · 4 blocked · 340 to score · ~US$0.44`, or `· all scored`) + **Start**; running shows `Scoring 719/1,342 · US$0.22` + **Stop** (`Stopping…` while the cancellation is in flight). Never a disabled Start beside a Stop. Continue in your AI is a handoff, not a feature of the companion: it holds the pre-qualification switch — a two-button segmented control, **Pre-qualified only** / **All jobs** — the sentence `48 of 1899 jobs found suitable for further review.` (`All 1899 jobs go on for review.` when the switch is off; `No shortlist yet: all 1899 jobs go on for review.` before any shortlist), then **Continue in Codex** / **Continue in Claude** (only for hosts installed on this Mac, `state.review.hosts`; the preferred host is the single primary once shortlisting completed) and **Copy prompt** as a text action beside them or the primary when neither host is installed. No help line. After completion this step is current; otherwise Shortlist is current. The scope count loads only while Jobs is on screen. Below the rail the toolbar holds only the three-way **Ranked | Applications | Blocked** segmented control (`aria-pressed` buttons styled like the Me category buttons). Controls that act on the list live on the list: the list column's head row (`.career-list-tools`) holds the labelled native **Sort** select (**Score**, default, or **Newest**) on the left and the **Clear reviews** text button on the right, above the status line. Ranked is the jobs list; Applications and Blocked reuse the same list + reader, and while either is active the rail, sort and Clear are hidden and disabled. The empty Ranked state points to the connected agent, not mandatory API setup. Below the toolbar a fixed two-pane grid (list `minmax(400px, 1fr)`, reader the rest) fills the remaining height: records scroll inside the list column, the Previous/Next bar is pinned at the column's foot and never moves between loading, loaded and end-of-list states, and the reader column is always rendered. On wide screens Next/Previous auto-opens the first record of the new page while focus stays on the list; with nothing open the reader says **Select a job** or **Select an application**. Narrow screens stack list then reader with **Back**. Sorting covers the whole saved union before pagination. The list status line reads `1–25 of 1,342 · 48 queued for AI review`.
- Pinned pagination is a CSS contract, independent of the renderer: `main` (flex 1, `min-height: 0`) → `#settings` (`height: 100%`) → `.career-view` (`height: 100%`, grid) → `.career-browser` (grid `auto minmax(0, 1fr)`; `#career-browser` adds a row for the rail: `auto auto minmax(0, 1fr)`) → `.career-panes` (grid item, stretched, `min-height: 0`; never `height: 100%`, which would measure the browser including its toolbar) → `.career-list` (grid `auto auto minmax(0, 1fr) auto`, `overflow: hidden`). Every list child is placed on an explicit `grid-row` (status head 2, retry and records 3, pagination 4) because `hidden` children leave the grid; implicit placement would hand the records the `auto` row, grow them to content height and push the pagination bar past the clipped column on tall windows. Only `(max-width: 479px)` or `(max-height: 639px)` switch the column to natural height and page scrolling.
- **Pre-qualification** (`#career-surface`, inside the last rail step) is the single control that decides which unreviewed jobs the MCP exposes to the agent. The user does not tune a number: **Pre-qualified only** (`#career-queue-qualified`) saves the qualifying score 36 as the minimum, **All jobs** (`#career-queue-all`) saves 0, through the same `prescan-threshold` operation; `aria-pressed` reflects the saved value. The live sentence beneath is `48 of 1,342 jobs go to your AI for full review; the rest are skipped.` (`All 1,342 jobs go to your AI. Shortlist first to skip poor matches.` only when no shortlist exists; the total counts catalogue jobs without a current review). After a profile change the old scores still apply and the sentence adds `· scored before your profile changed; shortlist again`. A failed save restores the pressed state and explains in the list status. The list's cutoff divider (`Not pre-qualified · skipped`) has no action; the switch above is the only control. Without the basic preferences the pre-filter scope line says to tell the agent the target roles, locations, work modes, relocation and travel, instead of a generic failure.
- One vocabulary, everywhere: **Shortlist** is the cheap Decisions pass that gives every job a **Score** (0–100); **AI review** is the user's own Codex/Claude reading the full adverts, which yields **Fit**; **Minimum score** is the threshold that decides which shortlisted jobs are **Queued for AI review** and which are **Skipped** so the agent does not spend inference on poor matches. The words pre-filter, priority, rank, hand over, next run and send do not appear in the interface (MCP tool names keep `prescan`). The Score sort orders the list by the number the user can see: every pre-filtered card shows its score in the right column, so the cutoff rule (`Not pre-qualified · skipped`) can be read against the numbers on either side of it; the reader repeats it as the verdict figure (`69 · Score`) beside the rule (`69 is below the qualifying score 36`). Queueing is user-owned: a job is queued when its score is at least the minimum (default 36) or when the user switched it on; the per-job **Review** switch overrides the threshold either way and the reader's **Reset** returns the job to the rule. Unscored jobs are excluded unless switched on; a predicted location conflict (`incompatible_location`) is unscored and overridable, an established one (saved review with a gate fail or relocation required against a refusal to relocate) has no switch at all. Without any current pre-scan every job is included. Decisions (pre-filter) scores and agent review scores are different scales and never share a control, a list or a chart. Incompatibility is either *predicted* or *established*: a pre-scan `Location conflict predicted` (or `Below your minimum`) row stays unscored but keeps its switch (`Review anyway`); a saved review with any gate fail, or relocation required while the user will not relocate, is established — never a candidate, no switch, overrides ignored, and the reader's Next run group reads `Not eligible for review: change your location or relocation preference to reconsider`.
- Card anatomy (`li.career-card`), left to right: (1) a 72px lead column (`.career-card-lead`) holding the **Review** switch — a native checkbox drawn as a 20px ruled square (`aria-label` "Queue {title} for AI review", Space toggles, clicks never open the record) with the 10px caption `Review` or `Review · manual` beneath it; the column stays, empty, on reviewed and ineligible rows so titles align. (2) The record button: a 36px company mark (`.career-card-mark`, facet rule, surface fill, the company's initial in mono; the organization's https logo drawn over it when the catalogue supplies `logoUrl`, removed on load error) beside three plain lines with 20px vertical padding and 8px gaps — role title (Geist 15/500); `company · Published 17 Oct 2026` (company ink-2, date ink); one Geist Mono 12px smoke line of facts joined by ` · ` (seniority, salary, city or location · work mode, commitment, classification), ellipsised to a single line, missing values omitted. No chips, boxes, uppercase or colour fills. (3) The 112px right column (`.career-card-side`), a sibling of the button, never nested inside it, holding only the number the list is sorted by: a reviewed job shows the overall fit as a 24px tabular Geist Mono figure (`.career-card-figure`) captioned `Fit` (`Fit · out of date` when stale; no decision text, no dimensions); a pre-filtered job shows its score the same way captioned `Score` (`Score · out of date` when stale); an unscored job shows, in the caption's place, the reason there is no score: Advert unavailable / Declined / Too large / Location conflict predicted / Below your minimum / Not pre-filtered. Logos are the one exception to the renderer's no-network rule: the page CSP allows `img-src https:` and `main.mjs` lets through `image` requests to https hosts only, with `referrerpolicy=no-referrer` and the in-memory session (no cookies); scripts, styles, fetches, frames and navigation stay local. The logo hosts are whatever the catalogue names (JobStash organization logos and website favicons), so showing the Jobs list reveals to those hosts which employers' logos were fetched, nothing else. An **ineligible** job (a review whose location match is `Location incompatible` or `Excluded by a gate`, or an established incompatibility from a stale review) shows that label alone in the column — a 12px ink caption (`.career-card-verdict`) wrapping within the column if it must — never the number and never a switch; its aria-label says `not eligible, {label}`. The **Score** sort lists current reviews by fit, then pre-filtered jobs by score, then unscored, then ineligible jobs last; an `li.career-cutoff` ruled divider (ink top rule, mono caption `Not pre-qualified · skipped`) sits before the first job scored below the qualifying score. **Job reader** (`#career-reader`): a candidate must see in one screen what the job is, where it stands and why, then the evidence. Order is fixed: (1) the serif title (role only) over the dispersion rule; (2) `.career-reader-meta` — one compact top line with `employer · Published 19 Oct 2026` in mono smoke and the text **Open job** action, then the same mono fact line as the card; (3) the **verdict** block (`section.career-verdict`, ink top rule and facet bottom rule, 16px vertical padding): a 36px tabular mono figure with its caption — `86 · Fit` for a current review, `69 · Score` for a shortlisted job, none otherwise — beside the headline (`Recommended` / `Needs clarification` / `Not recommended`; `Queued for AI review` / `Skipped`; `Location incompatible` / `Excluded by a gate`) and one detail line stating the rule (`Strong fit · 3 wins of 5 comparisons · Reviewed 14 Oct 2026`; `69 is below the qualifying score 36 · manual · scored before your profile changed`), then the agent’s saved reason in body type (prefixed `Reviewed at 83 before your profile changed ·` when that review is stale), then the **Queue for AI review** checkbox (`Review anyway` for a predicted location conflict; none for an established incompatibility or a current review) and **Reset** when overridden. An ineligible verdict is only its headline: no repeated not-eligible sentence, saved reason, Location or Relocation check. (4) **Checks**: one ledger of everything that can keep the job out — Location, Relocation, Salary (`pay · Below your minimum`), the three gates as Passes / Needs confirmation / Fails. (5) **Fit** chart (heading `Fit excluding location — not eligible` / `Fit — excluded by a gate` for ineligible reviews). (6) **Requirements**: compact ruled rows, label = `Missing · essential` style evidence word, value = the requirement wording, gaps first (contradicted, missing, transferable, demonstrated), plus a text **Add context** action. It copies a validated prompt for that exact saved requirement; the connected agent reads the job/current career, creates or reuses its application, asks one focused material-gap question, saves the answer as a reusable fact and reassesses the job. Success/error stays inline in that row; the Companion never creates a fact from an unstructured textbox. (7) **Your application**, only when one exists for the job: Prepared, CV draft, Cover letter, Exports, Interview answers — never a claimed submission. (8) Capture and the original advert for imports. (9) **Metadata**, only when a pre-filter row exists: `Scored · OpenAI Decisions · gpt-6-luna · current`. Identity, salary, place, mode, commitment and category appear once in the header/checks, never repeated as a Role ledger. **Block from evaluation** closes the reader. There is no separate Next run, Reviewed fit, Gates, Review reason or Pre-filter section. A reviewed job's **Fit** section is a horizontal bar chart (`div.career-chart`): one row per value — Overall first, then Direction, Capability, Scope, Preferences — with a 12px mono smoke label, a 12px track ruled in facet carrying an ink fill as wide as the score (ink for Overall, ink-2 for dimensions; CanvasText under forced colours), and the value right-aligned in tabular mono; for an ineligible job the chart heading is `Fit excluding location — not eligible` or `Fit — excluded by a gate`, the only place its number appears. No colour, no animation. Rows keep 44px hit areas, visible focus, `aria-current` on the open record and an aria-label summarising title, company, fit or rank and inclusion, and date. Captures are visible before review; incomplete cards show Needs full advert in the reader's Capture section rather than inventing an original or score.
- Blocking is user-owned and local. Commit the selection only on change, cancel any current scan, persist it locally and refresh the middleware-backed count/cost without automatically starting work. Preview reads catalogue metadata and cached results without provider calls or career-data mutation; invalidate it when context or publication period changes. Start recomputes the scope and scans only that snapshot. Concurrency and protocol batch sizes throttle work, not catalogue coverage.
- Pre-scans, form preparation and form filling run without an approval dialog; the scope line, the **Cost ESTIMATE** and `career_prescan_status` are the only billing surfaces. Saving a key never starts work; a missing key never blocks ordinary agent work or deterministic form preparation.
- The scope line is the single shortlist status: **N jobs in scope · M to score · ~US$0.31** before a run, **N jobs in scope · all scored** afterwards; `· K blocked` follows the scope count when the user blocked catalogue jobs, which are never pre-filtered. Costs use two decimals. Stop is visible only while a scan is starting or running; progress (**Scoring 719/1,342 · US$0.22**, blocked jobs excluded from the total) appears only then. A finished run shows no repeated summary, status label or token/request totals; stopped, failed or stale runs show one recovery line; a failed run names the provider's HTTP status when there is one. A transient provider failure on one job never stops the run: the job is retried, then recorded as unavailable and retried on the next Start. Never substitute a locally truncated list length for the middleware scope total.
- UI copy is action-first: button labels are one or two words that name the action (Start, Stop, Continue in Codex, Continue in Claude, Copy prompt, Clear reviews, Open job, Block job, Unblock, Back, Retry, Reset), actual state and a direct recovery action. Do not add repeated disclaimers about spending caps, preliminary results, sent-request billing or retained data to controls, approvals, statuses or errors. Keep technical behavior documented here and in the README rather than repeating it throughout the interface.
- Locked storage explains what is inaccessible and offers the actual unlock action. The native dialog remains for account pairing, form submission and update installation only: a square dialog, readable request details, cancel-first focus and a distinct allow action. Preparation, filling, pre-scans and CV sharing show no dialog.
- Account pairing returns to a one-time loopback browser page using the same bundled styles, fonts and logo. Its states are returning, awaiting native approval, connected and not completed; connected appears only after approval and platform activation succeed. No custom-protocol launch or installed browser extension is required for this return. Removing the fragment from browser history and rendering only success/failure must not expose career records or credentials.
- The Chrome extension is a compact dark side panel with one primary **Read page** action. The black rr toolbar icon grants `activeTab`, opens the panel and starts the same flow. It binds the page to the exact application before known-value preparation. **For this job** shows current CV/cover-letter PDFs and job-specific writing status; a small Claude/Codex selector and **Prepare this application** open the chosen host with a prefilled request. Say that the user must send it; an opened app is not generating. Current PDFs expose **Open** and **Show in Finder**, never invented upload success. Missing reusable contact details use native inputs and **Save details**; personal summaries/motivation answers belong to the application, not the profile. Keep typed drafts through updates. Secondary answer editing/copy/fill stays under closed **Review answers**; technical IDs, raw paths, source labels, API checkbox and a separate Prepare-values button are absent. No injected page overlay or custom paste/undo implementation.
- Form suggestions remain reviewable and selectable. Unknown, populated, protected and unsupported fields stay manual. A changed document/control/radio group invalidates filling. Native paste replaces the system clipboard with the focused empty field's prepared answer; no custom paste handler, input overlay or undo implementation. The user's AI may fill (`career_form_fill`) that Chrome tab without a dialog, and press an inspected submit/next control (`career_form_submit`) only behind the native confirmation. Display page observations, never inferred success from a generic thanks message. There is no autonomous bulk-application scheduler or security-check bypass. Uploads remain manual. New prose comes from the connected agent, not Decisions. Consent names the destination and the data released.
- Application identity is exact job ID/canonical URL or a recognized same-origin ATS job token, never hostname/employer/title alone. Existing current packages are reused. Changed originals/career context and missing/corrupt PDFs show stale or missing, not ready. Poll saved metadata only while the panel is open; saved answers trigger at most one current preparation, preserving edits. Deep links contain only the local request UUID, use supported host routes, and preserve host workspace/MCP trust prompts. Full adverts must be captured or retrieved from the exact source before writing. The extension does not operate a provider model or hold credentials.
- Updates shows the actual package version, Check / Download / Install actions and real progress. No public release is distinct from current; verified download, helper launch and new-version confirmation are separate states. Require native installation approval and preserve local data/identity. Local/source/manual installation limits and errors must be actionable, never fake success. Local bundles must not claim the production URL scheme.
